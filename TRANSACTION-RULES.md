# Transaction Rules

Рабочая карта известных правил классификации транзакций.

Цель документа:
- держать перед глазами актуальные сценарии в human-readable виде;
- быстро сверять бизнес-правило с текущим `config/sources.json`;
- явно показывать расхождения между текущим runtime-конфигом и уже согласованным target-поведением из тестов/specs.

Источник истины на текущий момент:
- runtime-конфиг: `config/sources.json`
- реализация: `src/apply/preview/tochka.ts`, `src/apply/preview/ruleEngine.ts`
- тесты: `src/apply/preview-*.test.ts` (по одному файлу на type_code)
- согласованный target для transfer-сценариев: `openspec/changes/preview-transfer-classification/specs/*`

Правила чтения таблиц:
- колонки `JSON logic эквивалент` и `JSON logic эквивалент (excluded)` показывают текущее выражение из `sources.json`;
- если сценарий уже согласован, но текущий `sources.json` ещё не полностью выражает его, это явно указано в колонке `Примечание`;
- `owned account` означает, что счёт найден в объединённой карте счетов всех настроенных банков (`config/sources.json → sources.*`) — реализовано custom-операцией `is_owned`;
- `deposit-like` означает счёт, начинающийся с `421` при BIC `044525104` (Точка) — реализовано custom-операцией `is_deposit`. Депозитная эвристика остаётся Точка-специфичной и не расширяется на другие банки.

Важно: `is_deposit` — это **строгое подмножество** `is_owned`. Функция `createAccountRegistry.isOwned` возвращает `true` для любого счёта с BIC `044525104`, начинающегося с `421`, без добавления его в `accountMappings`. Депозитные счета Точки автоматически открываются и закрываются, поэтому они не регистрируются в конфиге — ни в production, ни в тестах. Правило `NOT DEPOSIT_PAYER` в `excluded` нужно именно потому, что без него `is_owned(payer)` вернул бы `true` для депозитного счёта и deposit return был бы ошибочно excluded.

Сокращения в JSON logic:
- `OWNED_PAYER` = `{"is_owned":[{"var":"record.data.payerAccountId"},{"var":"record.data.payerBankBic"},{"var":"accountRegistry"}]}`
- `OWNED_PAYEE` = `{"is_owned":[{"var":"record.data.payeeAccountId"},{"var":"record.data.payeeBankBic"},{"var":"accountRegistry"}]}`
- `OWNED_RECIPIENT` = `{"is_owned":[{"var":"record.data.recipientAccountId"},null,{"var":"accountRegistry"}]}`
- `DEPOSIT_PAYER` = `{"is_deposit":[{"var":"record.data.payerAccountId"},{"var":"record.data.payerBankBic"}]}`
- `DEPOSIT_PAYEE` = `{"is_deposit":[{"var":"record.data.payeeAccountId"},{"var":"record.data.payeeBankBic"}]}`

## Маппинг категории honeymoney (`hmbee.categoryMapping`)

Резолюция категории для income/expense записей выполняется в `mapTochkaCategory` (`src/apply/preview/tochka.ts`) по слоям, от специфичного к общему; побеждает первый совпавший слой:

1. `rules` — массив расширенных правил `{ when, category, description? }` на JSON Logic над сырой записью (контекст `{ record }`, доступ `{"var": "record.data.<поле>"}`, как у `typeCodes`). Порядок в массиве = приоритет, применяется первое совпавшее правило. Доступен регистронезависимый regex-оператор `{"matches": [pattern, value]}` (`src/apply/preview/ruleEngine.ts`). Некорректный regex или условие не бросает исключение — правило просто не матчится, резолюция продолжается.
2. `title` — regex (case-insensitive) по `description` записи, первый совпавший паттерн.
3. `mcc` — lookup по MCC-коду.
4. Ничего не совпало → `category = null` → срабатывает «Missing category downgrade» (см. сквозные правила).

Дисциплина авторинга `rules`: правила должны быть узкими — включать проверку `type_code` (`{"==":[{"var":"record.meta_data.system_data.type_code"},"..."]}`) в дополнение к содержательному условию, иначе широкое правило перехватит записи, которые сейчас корректно ловятся `title`/`mcc`. Тесты: `src/apply/preview-category-rules.test.ts`.

## Что сейчас особенно важно помнить

- `PaymentIncome` — три явные OR-ветки в `included` (deposit return, deposit interest, external). `excluded` явно использует `NOT DEPOSIT_PAYER`, чтобы не захватить возврат тела депозита. Источник истины — `sources.json` и `preview-PaymentIncome.test.ts`.
- `PaymentWrittenOff` в текущем `sources.json` выражает deposit opening через `OWNED_PAYEE` (депозитный счёт ещё не в реестре, поэтому technically это `payer_owned AND payee_not_owned`, что работает случайно). Target-поведение задокументировано в тестах и specs.
- `SbpB2CPayment` в текущем `sources.json` описан одним broad include (`OWNED_PAYER`), а различение между «сторонний физлицо» и «мой внешний счёт» делается по общему списку моих счетов на этапе нормализации и в тестах.
- `PaymentClaim` — новый RS-тип, на который Точка перевела СМС-информирование и лицензионное вознаграждение (были `PaymentWrittenOff`). У него нет `corebankingId`/`payerBankBic`/`payeeBankBic`; `transactionId = claimId`, `description = purpose` (не `title`, который у `PaymentClaim` всегда `"No title"`). Исторические записи этих списаний под старым `type_code = PaymentWrittenOff` больше не попадают в категорию — повторная классификация прошлых периодов не планируется.

## Матчинг плановых транзакций

После стадий классификации (skip → match → create) каждая запись получает поле `planMatch` с полем `status`.

Порядок стадий:
1. **skip** — запись, уже внесённая в HM вручную (`reason = 'Внесена вручную'`), пропускается.
2. **match** — для оставшихся create-черновиков выполняется матчинг с неподтверждёнными плановыми транзакциями HM (`type=planned`, `real_amount=null`). Все записи бакета (account + direction + category + месяц) разрешаются совместно — жадно по ближайшей паре, независимо от порядка записей в файле.
3. **create** — runner отправляет в HM только create-черновики (`hmbee.id === null`); confirm-черновики (`hmbee.id !== null`) отложены до ручного подтверждения.

### Значения `MatchStatus`

| Статус | Значение |
| --- | --- |
| `matched-exact` | Найден ровно один план; сумма совпадает точно. Черновик становится confirm-формой. |
| `matched-tolerance` | Найден ровно один план; сумма попадает в допуск ±20% от `plan_amount`. Черновик становится confirm-формой. |
| `out-of-tolerance` | Кандидаты найдены (account + direction + category + месяц совпадают), но ни один не попал в допуск ±20%. Запись остаётся create-черновиком и видна в `--preview-planned`. |
| `ambiguous` | После применения tie-break (ближайшая сумма, затем дата) осталось >1 равнозначных кандидата. Запись остаётся create-черновиком и видна в `--preview-planned`. |
| `beaten-match` | Запись попадала в допуск плана, но проиграла конкуренцию другой записи с меньшей дистанцией. `planMatch.lostPlanId` — id оспоренного плана, `planMatch.beatenById` — `transactionId` победившей записи. Видна в `--preview-planned`. |
| `no-candidate` | Не найдено ни одного планового кандидата по ключу account + direction + category + месяц. Запись остаётся create-черновиком; в `--preview-planned` **не** отображается. |

Флаг `--preview-planned` показывает записи с `planMatch.status ≠ 'no-candidate'` (включая `beaten-match`) и несматченные планы из кеша за тот же период.

## Как поддерживать документ дальше

- При изменении business-правила сначала обновлять эту карту, потом `sources.json`, потом `sources.example.json`, потом тесты.
- Если один `type_code` покрывает несколько разных бизнес-сценариев, держать отдельные строки на каждый сценарий и отдельные OR-ветки в `sources.json`.
