## Context

См. `proposal.md` — мотивация. Здесь фиксируются только технические решения по двум независимым фиксам.

Текущий код:
- `src/adapters/tochka.ts` (`fetchPage`) строит `start_date`/`end_date` как `${date}T00:00:00.000Z` / `${date}T23:59:59.999Z` — буквальные UTC-границы, без привязки к `config.time_zone`.
- `src/apply/preview/tochka.ts` (`toDateInTimezone`) уже решает похожую задачу в обратном направлении: конвертирует ISO `event_date` в календарную дату (`YYYY-MM-DD`) в часовом поясе `config.time_zone`, через `Intl.DateTimeFormat`. Комментарий в коде отмечает, что это временное решение "до Node 26 и Temporal".
- `config/sources.json` → `sources.tochka.typeCodes.PaymentIncome.conditions` — правила `included`/`excluded`, разобранные в proposal.

## Goals / Non-Goals

**Goals:**
- Границы периода Tochka-синка и последующая нормализация даты транзакции должны использовать одно и то же понятие "календарного дня" — `config.time_zone` — чтобы не расходиться между этапами fetch и normalize.
- Входящий `PaymentIncome`-перевод от своего счёта в стороннем банке без адаптера синхронизации должен становиться save-ready transfer, а не теряться.

**Non-Goals:**
- Не создаём адаптер синхронизации для Райффайзена (и любого другого банка) — вне рамок этого изменения.
- Не меняем `HoneyMoneyCacheEntrySchema` и связанную с этим потерю `transfer_from_id`/`transfer_to_id` в кэше — отдельная, самостоятельная проблема (`manual-entry-skip`/`hmbee-transaction-cache`), обсуждалась в /opsx:explore, но не входит в этот change.
- Не меняем `PaymentAccepted` — асимметрия обоснована (см. proposal), исходящая нога не дублируется независимо от банка-получателя.
- Не мигрируем на Temporal — используем тот же `Intl`-подход, что уже применяется в `toDateInTimezone`.
- Не делаем автоматический ретроактивный пересинк уже обработанных периодов — это решение оператора, не часть кода.

## Decisions

### 1. Границы синка строятся через `config.time_zone`, а не через фиксированное смещение источника

Использовать `config.time_zone` (тот же параметр, что уже управляет нормализацией даты в `toDateInTimezone`), а не пытаться угадывать/жёстко прописывать собственное смещение Точки (`+05:00`, видимое в `event_date`).

Почему: у Точки `event_date` и `date` внутри одной и той же записи размечены в РАЗНЫХ смещениях (`+05:00` и `+03:00` соответственно) — источник сам не даёт единого "своего" пояса, на который можно опереться. А `config.time_zone` уже является единым источником истины для того, к какому календарному дню относится транзакция при нормализации. Если границы синка не будут согласованы с этим же поясом, `--from/--to X_X` и результат нормализации будут расходиться по построению — ровно то расхождение, из-за которого была потеряна транзакция.

Рассмотренная альтернатива: жёстко использовать смещение `+05:00`, наблюдаемое в `event_date`. Отклонено — это добавляет второе, ничем не обоснованное понятие пояса вместо переиспользования уже существующего конфигурационного, и не решает задачу теми же средствами, которыми она уже решена для нормализации.

Реализация: обратная операция к `toDateInTimezone` — по календарной дате (`YYYY-MM-DD`) и `time_zone` вычислить UTC-момент начала и конца этих суток в указанном поясе (тот же приём через `Intl.DateTimeFormat`, определение смещения на нужную дату). Разместить рядом с `toDateInTimezone` или в том же модуле, чтобbi логика перевода между "календарный день в поясе" и "UTC-момент" была в одном месте.

### 2. Разграничение `excluded`/`included` для `PaymentIncome` — по литеральному сравнению BIC, без нового оператора

Сузить `excluded` условием `payerBankBic == "<BIC Точки>"` и добавить симметричную `included`-ветку для `payerBankBic != "<BIC Точки>"` (при этом `is_owned(payer)` остаётся широкой кросс-банковской проверкой).

Почему так, а не новым jsonLogic-оператором вроде `is_same_bank`: паттерн литерального сравнения `payerBankBic` с BIC Точки уже используется в этом же правиле (существующая 2-я `included`-ветка). Добавление нового оператора внесло бы абстракцию, не нужную при уже устоявшемся паттерне в конфиге.

Рассмотренная альтернатива: сделать `is_owned` параметризуемым по конкретному банку (например, `is_owned_by_bank(account, bic, bankKey)`). Отклонено — `is_owned` используется в других местах (`getNormalizedType`/`isTransferMatched`) именно в широком, кросс-банковском смысле, и его семантику менять нельзя; вводить второй похожий оператор ради одного правила избыточно, когда буквенное сравнение BIC уже решает задачу.

## Risks / Trade-offs

- [Риск] Расширение окна синка может однократно "подтянуть" на день больше при повторном ручном ресинке уже обработанных периодов → Митигация: изменение затрагивает только вычисление границ, не логику пагинации (`page_count`/`last_date`), которая уже покрыта тестами; поведение остаётся детерминированным для одного и того же периода.
- [Риск] Новая `included`-ветка для `PaymentIncome` расширяет набор автоматически сохраняемых транзакций → Митигация: ветка применяется только к узкой, ранее НЕ обрабатываемой комбинации (`incoming=true`, плательщик "мой", но не Точка) — эта комбинация раньше молча терялась (excluded), а не намеренно игнорировалась, так что расширение не меняет поведение для существующих пользовательских сценариев.
- [Риск] Пересечение с `manual-entry-skip`: транзакция, ранее потерянная на этапе excluded, теперь дойдёт до skip-pass и может быть подавлена как "Внесена вручную", если в кэше Honey Money уже есть похожая запись (см. отдельно найденную неоднозначность ключа сопоставления переводов) → Вне рамок этого change; ключ сопоставления в `skipIndex.ts` не меняется.

## Engineering Constraints

- Новая функция построения границ периода должна быть чистой (принимать `date: string, timeZone: string`, возвращать ISO-строки), без побочных эффектов — тестируется юнит-тестами без моков сети.
- Никаких новых внешних зависимостей: переиспользуем `Intl.DateTimeFormat`, как в `toDateInTimezone`; не добавляем date-библиотеку.
- TypeScript strict mode: явные типы параметров/возврата у новой функции, без `any`.
- Изменение в `config/sources.json` — декларативное (JSON Logic), без нового кастомного оператора в `ruleEngine.ts`; следует уже принятому в файле стилю (литеральное сравнение BIC).
- `npm run check` (типы, Biome, тесты) остаётся Definition of Done; новые тесты добавляются рядом с существующими (`src/adapters/tochka.ts` → сосед `apply.test.ts`/новый файл для границ синка; `src/apply/preview/tochka.ts` → существующие тесты классификации переводов).
