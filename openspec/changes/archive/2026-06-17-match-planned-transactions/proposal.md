## Why

В Хани Мани часто заранее заведены плановые (в т.ч. рекуррентные) транзакции: аренда, подписки, школа и т.п. Когда приходит реальная банковская транзакция, её нужно сопоставить с такой плановой, чтобы в дальнейшем подтвердить план, а не создавать дубль. Сейчас `apply` об этом ничего не знает и для каждой реальной записи строит только `create`-черновик. Этот change добавляет сам матчинг (real → неподтверждённый план) в базовый пайплайн и делает результат видимым в `--preview`, не выполняя запись подтверждения (она — в отдельном следующем change).

## What Changes

- В базовый пайплайн нормализации/preview добавляется дефолтный матчер: для каждой реальной транзакции ищется ближайший неподтверждённый план из кеша Хани Мани.
- Ключ матчинга по умолчанию: `account_id + direction + category + сумма в пределах ±20%`, окно — календарный месяц транзакции, сопоставление 1:1, при нескольких кандидатах — ближайший по дате, затем по сумме.
- Кандидаты — только неподтверждённые планы из кеша: `type=planned`, есть `plan_amount`, `real_amount == null` (зеркало индекса skip из `manual-entry-skip`).
- При матче `hmbee` (единый source of truth того, что уходит в ХМ) принимает **confirm-форму**: несёт `id` плана, `type=planned`, `plan_amount`, `common_id`, `virtual_id` (из плана) + `real_amount`=сумма банка + `date`=дата факта. Create vs confirm различается наличием `id` (`null` = создать, число = обновить) — как в API ХМ. Отдельный объект `plannedMatch` не вводится.
- `PreviewRecord` получает лёгкое поле `plannedMatchStatus` для отчёта/фильтра: `matched-exact` | `matched-tolerance` | `no-candidate` | `out-of-tolerance` | `ambiguous` (отдельный объект под матчинг не вводим — пока это только статус).
- Сматченная с планом транзакция формируется по обычным правилам: `identified=true, save=true, reason=null`, а `hmbee` = confirm-форма. Реальная отправка confirm не выполняется в этом change — это решается **на уровне раннера**: `apply` исполняет только create-черновики (`hmbee.id == null`), а confirm-черновики (`id != null`) формируются и помечаются `save=true`, но раннер их пока не отправляет (исполнение confirm + спайк — следующий change).
- `out-of-tolerance` и `ambiguous` матчем не считаются → создаются как обычные записи (`save=true`), но как кандидаты попадают в вывод `--preview-planned`.
- Добавляется флаг-фильтр `apply <source> --preview-planned`: показывает сматченные записи, кандидатов (`out-of-tolerance`/`ambiguous`) и несматченные плановые транзакции источника за рассматриваемый период.

## Capabilities

### New Capabilities
- `planned-transaction-matching`: сопоставление реальной транзакции с ближайшим неподтверждённым планом Хани Мани по дефолтному алгоритму; при матче `hmbee` принимает confirm-форму (с `id` плана), запись удерживается от создания дубля, статус матча отражается в `PreviewRecord`.

### Modified Capabilities
- `source-preview`: предпросмотр показывает результат матчинга планов (конечное HM-представление как confirm плана `id` против create), и появляется фильтр `--preview-planned`, выводящий сматченные записи, кандидатов и несматченные планы источника.
- `source-apply`: раннер записи исполняет только create-черновики (`hmbee.id == null`); confirm-черновики (`id != null`) формируются и помечаются `save=true`, но их отправка отложена до отдельного change.

## Impact

- Код: модуль матчера планов (срез кеша неподтверждённых планов, ключ, окно месяца, tie-break, 1:1), расширение типа `hmbee`/`HoneyMoneyTransaction` confirm-формой (`id`/`type=planned`/`plan_amount`/`common_id`/`virtual_id`) + поле `plannedMatchStatus` в `PreviewRecord` (`src/apply/preview/types.ts`), проводка матчинга в пайплайн `apply`/preview, гард раннера «только create-черновики» (`src/index.ts`, `src/apply/preview/*`), флаг `--preview-planned`.
- Переиспользуется: загрузка кеша `sync/hmbee/all_json_cache.json` и нормализация даты/суммы из `manual-entry-skip` (HMB-24).
- Вне охвата (отдельные change): запись подтверждения плана (POST с `id`, `confirmPlannedTransaction`) и спайк минимального POST; расширенный конфиг матчинга (per-план tolerance, counterparty-bridge); слияния «1 реальная → N планов».
- Качество: Definition of Done — `npm run check` (Biome lint+format, TypeScript strict, тесты) зелёный; матчер покрыт unit-тестами (ключ, ±20%, окно месяца, tie-break, 1:1, статусы) в стиле `preview-*.test.ts`.
