## Context

Резолюция категории honeymoney для записей Точки выполняется в `mapTochkaCategory` (`src/apply/preview/tochka.ts`) и сейчас использует два слоя:

```
mapTochkaCategory(description, mcc, categoryMapping)
  ├── 1. title regex (первый матч побеждает)
  ├── 2. mcc lookup
  └── 3. null → save=false
```

Оба слоя видят лишь узкий срез записи: `description` (= `title`) и `mcc`. Сырая запись `sourceRecord` до маппера не доходит, хотя доступна у вызывающего кода в `buildHoneyMoneyIncomeExpenseTransaction`.

В проекте уже есть работающая инфраструктура JSON Logic: `evaluateRule({ record, accountRegistry })` в `src/apply/preview/ruleEngine.ts` с кастомными операциями `is_owned`, `is_deposit`. Она используется для `typeCodes`-правил классификации (included/excluded) и оперирует контекстом `{ record }`. Тот же движок переиспользуется для нового слоя.

## Goals / Non-Goals

**Goals:**
- Добавить третий слой резолюции — расширенные правила на JSON Logic по произвольным полям записи (`purpose`, `phoneNumber`, `cardPanPart`, …).
- Приоритет `rules → title → mcc` (узкое → общее). Дополнить, а не заменить текущую логику.
- Переиспользовать существующий `evaluateRule` и его контекст `{ record }`.
- Регистронезависимый поиск подстрок/паттернов в текстовых полях через новый оператор `matches`.
- Полная обратная совместимость: конфиг без `rules` валиден.

**Non-Goals:**
- Доработка скрипта `map:tochka` (создание правил, авто-пропуск покрытых записей) — отдельная задача.
- Изменение слоёв `title`/`mcc` и их взаимного приоритета.
- Runtime-использование `ignored` (он был и остаётся скриптовым).
- Доступ правил к нормализованным полям (`amount`, `type`) — пока только сырой `record`.

## Decisions

### Решение 1: `rules` — массив, а не объект
`mcc` и `title` — это `Record<string, MappingEntry>` со строковым ключом. У правила нет естественного строкового ключа (условие — это JSON Logic-объект), и порядок важен: первый совпавший выигрывает. Поэтому `rules: RuleEntry[]`, где `RuleEntry = { when: JsonLogic; category: string; description?: string }`.

_Альтернатива:_ объект с произвольными ключами-именами. Отклонено — порядок в JSON-объектах формально не гарантирован спекой, а приоритет здесь критичен.

### Решение 2: Порядок `rules → title → mcc`
Правила проверяются **первыми**, потому что они самые специфичные (точечное условие по `purpose`/`phoneNumber`), а title — regex по общему полю. Это согласуется с уже принятым в проекте принципом «специфичное раньше общего» (title приоритетнее MCC).

Следствие и осознанный компромисс: слой `rules` становится самым мощным и потенциально перехватывает то, что раньше ловилось title/mcc. Дисциплина — правила должны быть узкими; формат этого не гарантирует, только автор конфига. Отражено в Risks.

_Альтернатива:_ `title → mcc → rules` (как в первой формулировке пользователя). Отклонено: примеры с `Банк Точка` матчатся по title раньше, и до правила по `purpose` дело бы не дошло.

### Решение 3: Контекст правила — `{ record }`, как у `typeCodes`
Правила получают тот же контекст, что и `typeCodes`: сырую запись под `record`. `{"var": "record.data.purpose"}` работает из коробки, движок трогать не нужно. Нормализованные поля (`amount`, `type`) в контекст не добавляются в этом change — при появлении реального кейса расширим.

_Альтернатива:_ `{ record, normalized }`. Отклонено сейчас как преждевременное; сырое `record.data.sum` доступно, если понадобится сумма.

### Решение 4: Кастомный оператор `matches`
Встроенный `in` в json-logic-js — это case-sensitive `indexOf`. Для банковских формулировок в `purpose` нужен регистронезависимый и по возможности regex-матчинг. Добавляем `jsonLogic.add_operation('matches', (pattern, value) => new RegExp(pattern, 'i').test(String(value)))` в `ruleEngine.ts`, по образцу `is_owned`/`is_deposit`. Некорректный паттерн ловится существующим `try/catch` в `evaluateRule` → правило не матчится. Голые `==`/`in` остаются доступны для точных сравнений (`cardPanPart`, `phoneNumber`).

### Решение 5: Проброс `sourceRecord` в `mapTochkaCategory`
Сигнатура меняется: `mapTochkaCategory(sourceRecord, description, mcc, categoryMapping)`. Правила прогоняются через `evaluateRule(rule.when, { record: sourceRecord, accountRegistry })`. `accountRegistry` уже доступен в опциях нормализации.

### Решение 6: Резолв правил при загрузке конфига
Zod-схемы `categoryMappingSchema` и `ResolvedCategoryMappingSchema` расширяются полем `rules` (default `[]`). В отличие от `title`, правила не требуют предкомпиляции regex на этапе загрузки — `when` остаётся сырым JSON Logic и интерпретируется движком (сам regex внутри `matches` компилируется в рантайме, как и в существующих `typeCodes`). Тип `CategoryMapping` (сейчас `Omit<..., 'ignored'>`) включает `rules`.

## Risks / Trade-offs

- **Слишком широкое правило перехватывает title/mcc-кейсы** → Митигация: документировать в спеке, что правила должны быть узкими; порядок «первый матч побеждает» делает поведение предсказуемым; preview-тесты фиксируют приоритет rules над title.
- **Некорректный regex/JSON Logic в конфиге** → Митигация: `evaluateRule` уже оборачивает `jsonLogic.apply` в `try/catch` и возвращает `false` при ошибке — сбойное правило просто не матчится, резолюция падает на следующий слой.
- **Расхождение оператора `matches` между рантаймом и будущим скриптом** → Вне объёма; помечено как follow-up для `map:tochka`. Скрипт json-logic пока не использует.
- **`record.data.purpose` отсутствует у части типов записей** → json-logic `var` вернёт `null`/`undefined`, `matches`/`==` дадут `false` — правило корректно не сработает, без исключений.

## Migration Plan

- Чисто аддитивное изменение. Существующие конфиги без `rules` продолжают работать (default `[]`, слой пропускается).
- Rollback — обратимо: удаление ключа `rules` из конфига отключает слой без изменения кода; откат кода не ломает существующие данные.

## Open Questions

- Нужен ли правилам доступ к нормализованным `amount`/`type` — отложено до реального кейса (Решение 3).
- Форма расширения скрипта `map:tochka` под создание правил — отдельная задача.
