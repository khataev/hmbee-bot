## Context

Три связанные шероховатости в CLI-потоке `sync` → `apply`:

1. **Дубли при повторном `apply`.** HM-кэш (`sync/hmbee/all_json_cache.json`) — снимок существующих транзакций Honey Money, используемый skip-pass в `apply` для пометки уже внесённых записей (`reason = "Внесена вручную"`). Кэш не обновляется автоматически после `apply`. Если оператор забыл обновить его вручную (через `sync --update-hmbee-cache`), повторный `apply` отправляет только что созданные записи заново.

2. **`sync` не чистит старый файл.** Loader (`loadSyncFiles`) требует ровно один `*.json` в `sync/<source>/` и падает при нескольких. Повторный `sync` с другим диапазоном оставляет старый файл → `apply` ломается до ручного удаления.

3. **Лишнее ветвление в печати проблемных записей.** В `index.ts` id/описание берутся то из `normalized`, то через `describeSourceRecord`, хотя для проблемных записей оба пути дают идентичный результат (оба опираются на `getTransactionId`/`getDescription`).

Ключевой факт для (1): skip-pass читает кэш рано — `loadCache()` на `index.ts:141`, до развилки preview/send. Значит обновление кэша обязано стоять **до** этой точки, иначе оно не повлияет на решения о пропуске.

## Goals / Non-Goals

**Goals:**
- Исключить дубли: `apply` всегда работает на актуальном HM-кэше.
- Сделать `sync` самодостаточным относительно инварианта «один файл».
- Убрать дублирующее ветвление печати проблемных записей.
- Дать явный опт-аут для офлайн/тестовых прогонов `apply`.

**Non-Goals:**
- Не меняем формат кэша, схему `NormalizedRecord` или контракт `hmbee`-черновика.
- Не делаем `normalized` обязательным полем `PreviewRecord` (остаётся опциональным).
- Не типизируем `PreviewRecord.sourceRecord` (остаётся `unknown`, каст сохраняется) — вне скоупа.
- Не трогаем логику планов/матчинга сверх переиспользования свежего кэша.

## Decisions

### 1. Обновление HM-кэша выполняет `apply` перед skip-pass, на любом запуске

Refresh встаёт **до** `loadCache()` (`index.ts:141`), поэтому skip-pass и planned-pass видят свежие данные. Выполняется на всех режимах, включая `--preview`/`--preview-planned`, — так preview показывает те же skip-решения, что и реальная отправка.

**Почему до отправки, а не после:** обновление перед решением о пропуске фиксирует фактическое состояние HM в этот момент — включая прошлый `apply` и ручной ввод в UI. Вариант «после `apply`» ломается при падении на середине отправки.

**Почему сеть в `apply` не проблема:** реальная отправка и так требует связи с HM (`dispatchTransaction`), поэтому предшествующий refresh не добавляет новой зависимости. Отсюда обработка ошибок: **отказ refresh прерывает `apply`** (не работаем на устаревшем кэше). Для preview это означает новую зависимость от сети/кредов — осознанный компромисс, закрытый опт-аутом.

_Альтернатива (отклонено):_ refresh только на send-пути. Оставляла бы preview офлайн, но preview показывал бы skip-решения, расходящиеся с реальным apply. Выбран единообразный refresh + опт-аут.

### 2. Опт-аут `--skip-hmbee-cache-update` на `apply`

Единый флаг закрывает обе потребности: пропуск сети в preview и офлайн/тестовые прогоны на существующем кэше. По умолчанию refresh форсится (защита от забывчивости — исходная причина change). Под флагом `apply` работает на текущем содержимом кэша, как раньше.

### 3. Граница обрезки (`from`) — из имени sync-файла

`trimEntries(all, from)` требует `from`. У `apply` нет опции `--from`, но имя файла `sync/<source>/<from>_<to>.json` уже кодирует диапазон. Это сохраняет паритет с обрезкой, которую делал `sync --update-hmbee-cache`.

_Альтернативы (отклонено):_ минимальная `normalized.date` среди записей — ненадёжна (записи с ошибкой нормализации имеют `date = undefined`); отказ от обрезки — расходится с поведением, к которому привык кэш.

### 4. Loader возвращает данные вместе с границами интервала

`loadSyncFiles` меняет контракт: вместо `TochkaSyncRecord[]` возвращает записи вместе с распарсенными `from`/`to` (например `{ records, from, to }`). Loader уже единолично резолвит единственный файл — он и есть естественное место разбора имени. `apply` получает `from` из этого результата, без повторного парсинга в `index.ts`.

### 5. Автоочистка в `sync`

Перед записью нового файла `sync` удаляет прочие `*.json` в `sync/<source>/`. Скоуп строго на подкаталог источника — `sync/hmbee/` (кэш) не затрагивается. Только файловый режим; при `--stdout` директория не трогается. Согласуется с инвариантом loader «ровно один файл».

### 6. Печать проблемных записей — всегда через `describeSourceRecord`

Ветвление на `normalized` убирается; id/описание всегда берутся `describeSourceRecord(record.sourceRecord as TochkaSyncRecord)`. Для проблемных записей результат идентичен прежней ветке через `normalized`. Требования (печатать id, описание, reason) не меняются — это чистый рефакторинг.

## Engineering Constraints

- **Type safety (strict).** Новый возвращаемый тип `loadSyncFiles` объявляется явным интерфейсом; все потребители обновляются. Каст `as TochkaSyncRecord` в печати сохраняется (типизация `sourceRecord` вне скоупа).
- **Module boundaries.** Обрезка кэша остаётся в `src/hmbee/cache.ts` (`trimEntries`/`writeCache`) и переиспользуется из `apply` — без дублирования логики. Разбор имени файла живёт в `loader.ts`, а не в `index.ts`.
- **Error handling.** Отказ refresh в `apply` — прерывание с классифицированной ошибкой (как существующие ветки `Apply failed: …`), без утечки секретов. Отсутствие/некорректность даты в имени файла обрабатывается явной ошибкой.
- **Style/lint.** Новые ветки следуют STYLE-GUIDE; `npm run check` (Biome + tsc strict) — обязательный gate. Новых внешних зависимостей нет.

## Risks / Trade-offs

- **[preview требует сеть/креды]** → опт-аут `--skip-hmbee-cache-update`; поведение задокументировано.
- **[BREAKING: удаление `--update-hmbee-cache`]** → флаг убирается из `sync`; упоминания в README/скриптах/TECH-DEBT обновляются в рамках задач. Пользовательских скриптов, завязанных на флаг, в репозитории нет (проверяется).
- **[apply чаще ходит в HM]** → приемлемо: send и так требует HM; для preview есть опт-аут.
- **[некорректное имя sync-файла ломает разбор `from`]** → loader кидает явную ошибку; автоочистка в `sync` (решение 5) снижает вероятность «мусорных» файлов рядом.
