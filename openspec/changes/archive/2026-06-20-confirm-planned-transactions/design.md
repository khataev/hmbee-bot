## Context

`match-planned-transactions` уже строит для сматченной записи confirm-черновик `hmbee` (с `id` плана), но раннер его не отправляет — отсрочка была временной. Этот change включает реальную отправку подтверждения.

Формат тела подтверждён **ручным спайком** на реальном API (тестовый рекуррентный план `id 2580985713`, недельный, `end_date 2026-06-28`). Результаты:
- Лин-боди **без** `user_id, created_from, created_at, updated_at, planned_repeat_end_times` принят (`status: "success"`).
- Сервер сам сохранил `created_at` и обновил `updated_at` (мы их не слали) → риск stale-блокировки снят.
- Эхо-нутые `planned_repeat_days:7 / end:"date" / end_date:"2026-06-28"` сохранены; `real_amount` встал, серия не пострадала.

Эндпоинт тот же, что у create (`POST /transaction`); create vs confirm различает наличие `id`.

## Goals / Non-Goals

**Goals:**
- `apply` отправляет confirm-черновики (POST с `id`), подтверждая планы вместо дублей.
- Тело — лин-форма: эхо плана + впрыск `real_amount`/`date`, `description` из маппинга.
- Кеш хранит поля повтора для эхо; confirm-типы приведены к реальным значениям повтора и `common_id: string`.

**Non-Goals:**
- Расширенный конфиг матчинга (per-план tolerance, counterparty-bridge).
- Слияния «1 реальная → N планов».
- Изменение категории плана при подтверждении.

## Decisions

### 1. Лин-боди (по результату спайка)
Шлём только поля формы `HoneyMoneyTransaction`; серверные пять полей не шлём — сервер ведёт их сам. Это снимает и вопрос про stale `updated_at`.

### 2. Эхо повтора из плана, не литералы
`planned_repeat_days/end/end_date` берём из плана (спайк показал, что они сохраняются и важны для рекуррентного инстанса). Поэтому кеш обязан их хранить (раньше срезались) и confirm-типы должны допускать реальные значения, а не литералы `0/'always'/null`.

### 3. `date` = дате банка
Подтверждение сдвигает дату инстанса на дату реальной транзакции (подтверждённое ранее положение). `id`/`common_id` сохраняются, поэтому инстанс остаётся в своей серии.

### 4. `description` из маппинга
Строим как у create (`${absAmount} ${mappedDesc}`). Текущий `buildConfirmHmbee` берёт `description` из create-черновика — менять не нужно.

### 5. Одна отправка, маршрут по `id`
Раннер для каждой save-ready записи: `hmbee.id == null` → create-путь; `id != null` → confirm-путь (POST тем же эндпоинтом). Снимаем гард «только create».

### 6. Парсер ответа
Ответ confirm крупнее (с `accounts`/`virtuals`/`checkpoints`), но нам нужны `data.transaction.id` и `status: "success"` — те же, что у create; парсер лёгкий и общий.

### 7. Режим `--one-by-one` (ручное подтверждение)
Модификатор non-preview apply: перед каждой отправкой (create или confirm) печатаем **однострочную** сводку записи и спрашиваем оператора через stdin. Формат строки: `дата · subtype(e/i/t) · категория · description` (из `hmbee`), с пометкой create/confirm (для confirm — id плана). Например: `2026-05-02 · e · Аренда квартиры · 31000 [confirm #2580…]`. Минимальный набор ответов: `y` (отправить), `n` (пропустить), `q` (выйти, не отправляя остальные); опционально `a` (отправить все оставшиеся без вопросов). Назначение — отладочная страховка на первых прогонах: не залить всё разом и не вычищать ошибки из Хани Мани вручную. С `--preview`/`--preview-planned` режим инертен (записи нет). Реализация — readline в `src/index.ts`; цикл отправки уже последовательный.

## Risks / Trade-offs

- **Сдвиг даты у рекуррентного инстанса.** Спайк дату не двигал. → На первом реальном прогоне проверить, что сдвиг `date` на дату банка не задевает соседние инстансы серии (низкий риск: `id`/`common_id` сохраняются).
- **Устаревший кеш.** Подтверждаем план, которого в актуальном HM уже может не быть (или уже подтверждён). → Та же дисциплина `sync --update-hmbee-cache`; повторный confirm того же `id` — идемпотентный upsert.
- **`out-of-tolerance`/`ambiguous` по-прежнему создаются** (не подтверждаются) — без изменений; видны в `--preview-planned`.
