## Context

Текущий матчинг ([src/hmbee/plannedMatcher.ts](../../../src/hmbee/plannedMatcher.ts)) — потоковый: `applyMatchPass` идёт `records.map`, для каждой реальной транзакции дёргает `matchPlannedTransaction`, который берёт план-кандидаты из бакета индекса (`account_id|subtype|category|yearMonth`), фильтрует по допуску ±20%, выбирает лучший через `selectBest` и **немедленно выпиливает** план из индекса (`splice`).

Эта мутация в порядке записей файла делает решение зависимым от очерёдности: реальная, идущая в файле раньше, занимает план в пределах допуска, даже если для этого плана существует более точный претендент, который придёт позже. `selectBest` уже умеет разрешать конкуренцию **планов за одну реальную** (нечего по дате, затем по сумме), но обратное направление — **реальных за один план** — не разрешается вовсе, отдано порядку файла.

Бакеты в реальных данных крошечные (обычно 1–3 реальных × 1–3 плана), что снимает любые опасения по производительности и делает корректность единственным значимым критерием.

## Goals / Non-Goals

**Goals:**
- Убрать зависимость результата матчинга от порядка записей в файле.
- Разрешать конкуренцию нескольких реальных за один план по близости (дистанция: сумма, затем дата), симметрично существующему разрешению планов за реальную.
- Сохранить и очистить семантику `ambiguous`: только истинные ничьи, симметрично в обе стороны.
- Дать отладочный след для вытесненной реальной (`beaten-match` + `lostPlanId` + `beatenById`).

**Non-Goals:**
- Не сужаем и не меняем сам допуск ±20% — одиночный «разовый» платёж, случайно близкий к плану и не имеющий конкурента, по-прежнему может сматчиться (это отдельная ось проблемы, вне рамок данного изменения).
- Не вводим оптимальное назначение (Вариант C) — см. Decisions.
- Не меняем ключ бакета, набор кандидатов (только unconfirmed-планы) и формат confirm-черновика.

## Decisions

### Решение 1: Greedy quality-first (Вариант A), а не оптимальное назначение (Вариант C)

Переходим на двухфазную обработку с жадным разбором рёбер по качеству:

```
Фаза 1 — собрать:  records → Map<bucketKey, Real[]>   (группировка по ключу бакета)
Фаза 2 — разрешить каждый бакет независимо:
           построить рёбра real↔plan (план в допуске), вес = дистанция
           пока есть рёбра среди свободных концов:
               взять глобально минимальное ребро → consume(real, plan)
Фаза 3 — записать исходы обратно в records
```

**Почему A, а не C (оптимальное назначение / венгерский алгоритм):** A и C расходятся только в «обездоливающем» corner-case — когда жадно схваченное дешёвое ребро лишает третью реальную её *единственного* плана и теряет матч целиком. Чтобы это возникло, нужна реальная, дотягивающаяся до ≥2 планов, и другая реальная, чей единственный достижимый план — тот, что жадность отдала первой. Под допуском ±20% по разным суммам планов окна пересекаются редко, поэтому конфигурация маловероятна в наших данных. C добавил бы рекурсию/перебор и копил бы все оптимальные распределения; выгода не оправдывает сложность. **C зафиксирован как fallback** на случай, если обездоливающие кейсы реально проявятся — подробный разбор и контрпример вынесены в долгоживущий `TECH-DEBT.md` (пункт 8), чтобы пережить архивацию этого change.

**Альтернатива — plan-first жадность** (для каждого плана выбрать лучшую реальную): чинит репортнутый баг, но это просто другая жадность, не более корректная, чем quality-first, и менее естественно ложится на существующий `selectBest`. Отвергнуто.

### Решение 2: Дистанция = сумма, затем дата

Вес ребра — близость по сумме (`|sourceAbs − planAbs|`), тай-брейк по близости даты. Точная сумма — сильнейший сигнал исполнения плана. Это сохраняет уже принятый в `selectBest` приоритет (текущий код сортирует дата → сумма; при бакетном разрешении логичнее сумма → дата, поскольку рёбра ранжируются глобально по силе совпадения). Обе вторичны и переиспользуют существующие хелперы.

### Решение 3: `ambiguous` через ту же проверку на ничью, но поверх бакета

`ambiguous` срабатывает только когда **минимальная дистанция достигается на >1 ребре, делящих общий конец** (одна реальная между двумя равноудалёнными планами ИЛИ один план между двумя равноудалёнными реальными). Это та же логика, что `selectBest` применяет сегодня, поднятая на уровень бакета и симметризованная. Разные суммы дают разные дистанции и единственного победителя — поэтому в большинстве бакетов `ambiguous` не возникает.

### Решение 4: Новый исход `beaten-match` и структура `PlanMatch`

Реальная, имевшая план в допуске, но проигравшая конкуренцию, получает `beaten-match` (а не `out-of-tolerance` по остаточному принципу и не `no-candidate`, который скрыл бы её из planned-view). Плоское поле заменяется объектом:

```ts
interface PlanMatch {
  status: 'matched-exact' | 'matched-tolerance' | 'no-candidate'
        | 'out-of-tolerance' | 'ambiguous' | 'beaten-match';
  lostPlanId?: number;   // id оспоренного и проигранного плана; только при beaten-match
  beatenById?: string;   // normalized.transactionId победившей реальной; только при beaten-match
}
```

`lostPlanId` и `beatenById` указывают на два конца оспоренного ребра. Оба избыточны через join-ключ (`plan.id == hmbee.id` победителя), но оставлены оба ради удобства отладки. `lostPlanId` НЕ заполняется для выигранных матчей — там план уже лежит в `hmbee.id`. `beatenById` имеет тип `string`, как `normalized.transactionId` ([src/apply/preview/types.ts](../../../src/apply/preview/types.ts)).

## Risks / Trade-offs

- **Жадность субоптимальна в обездоливающем кейсе** → Mitigation: проверено, что под ±20% это маловероятно; Вариант C задокументирован как fallback при появлении реальных случаев.
- **Допуск ±20% остаётся широким** → Mitigation: вне рамок изменения; конкуренция чинит случаи с присутствующим точным претендентом, что покрывает репортнутый баг. Одиночный ложный матч без конкурента — известное ограничение, зафиксировано в Non-Goals.
- **BREAKING: переименование `plannedMatchStatus` → `planMatch`** → Mitigation: поле внутреннее (PreviewRecord), не часть внешнего контракта; все потребители (`previewPlanned.ts`, тесты) обновляются в этом же изменении.
- **Изменение приоритета тай-брейка (дата→сумма ⇒ сумма→дата)** → Mitigation: затрагивает только мультикандидатные бакеты; покрывается тестами, поведение для одиночных бакетов неизменно.

## Migration Plan

Изменение целиком внутри препроцессинга preview, без персистентного состояния и внешних контрактов. Деплой — обычный релиз CLI. Откат — реверт коммита; артефакты кэша и формат вывода не меняются необратимо.

## Engineering Constraints

- **Type safety**: строгий TypeScript; `PlanMatch.status` — строковый union, исчерпывающе обрабатываемый; `lostPlanId`/`beatenById` опциональны и присутствуют только при `beaten-match` (инвариант проверяется в тестах). Без `any`.
- **Error handling**: матчинг чистый и тотальный — пустой бакет, нет рёбер, ничья дают явные статусы (`no-candidate`/`out-of-tolerance`/`ambiguous`), а не исключения. Мутация общего индекса заменяется локальным потреблением в пределах бакета, чтобы исключить побочные эффекты между бакетами.
- **Module boundaries**: бакетное разрешение живёт в `plannedMatcher.ts`; `plannedIndex.ts` остаётся ответственным за построение/чтение индекса и сбор непотреблённых планов; `previewPlanned.ts` лишь читает `planMatch.status`. Тип `PlanMatch` объявляется в `src/apply/preview/types.ts` рядом с `PreviewRecord`.
- **Style / lint**: новый код проходит Biome и `npm run check`; следует STYLE-GUIDE.md и правилам TRANSACTION-RULES.md. Новых внешних зависимостей нет.
