## Why

Матчинг плановых транзакций жадно расходует планы в порядке записей JSON-файла: каждая реальная транзакция обрабатывается изолированно и немедленно выпиливает выбранный план из индекса. Из-за этого реальная, пришедшая в файле раньше, может занять чужой план в пределах допуска ±20%, а точный претендент, пришедший позже, остаётся ни с чем.

Конкретный баг (июнь 2026, бакет `2053036|e|Банки|2026-06`, планы −950 и −100): разовая комиссия 1000 руб обрабатывается раньше ежемесячной лицензии 950 руб. `|1000−950|=50 ≤ 0.2×950=190` → 1000 жадно забирает план −950; когда доходит до 950 руб, остаётся только план −100 → `out-of-tolerance`. Точный матч (дистанция 0) проигрывает случайному порядку файла.

## What Changes

- Матчинг переходит на **двухфазное бакетное разрешение** вместо потоковой обработки «одна реальная за раз»:
  - Фаза 1: matchable-реальные группируются по ключу бакета (`account_id|subtype|category|yearMonth`).
  - Фаза 2: внутри бакета строится двудольный граф real↔plan (ребро = план в допуске, вес = дистанция по сумме, затем дате); планы разбираются жадно по качеству — глобально минимальное ребро первым, затем consume обоих концов, повтор.
  - Фаза 3: исходы записываются обратно в записи.
- Конкуренция нескольких реальных за один план теперь видима и разрешается по близости (симметрично уже существующему разрешению нескольких планов за одну реальную).
- `ambiguous` очищается и становится симметричным: ложные срабатывания от порядка файла уходят; истинные ничьи (равные дистанции на общем конце) остаются; впервые детектируется ничья «две одинаковые реальные за один план».
- Вводится новый исход `beaten-match` для реальной, которая имела план в допуске, но проиграла конкуренцию более точной реальной (раньше такая получала бы `out-of-tolerance` по остаточному принципу).
- **BREAKING**: поле `PreviewRecord.plannedMatchStatus?: MatchStatus` заменяется объектом `PreviewRecord.planMatch?: PlanMatch`, несущим `status`, а также `lostPlanId` и `beatenById` для отладки `beaten-match`.
