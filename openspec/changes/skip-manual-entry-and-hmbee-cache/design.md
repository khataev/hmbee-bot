## Context

Сейчас `apply <source>` грузит нормализованные записи из `sync/<source>/*` и пишет каждую identified+save запись в Хани Мани через `HoneyMoneyClient.createTransaction`. Состояние Хани Мани при этом не читается, поэтому транзакции, уже внесённые оператором вручную (обычные или подтверждённые плановые), создаются повторно.

Хани Мани отдаёт всю историю транзакций одной ручкой `all_json.json` (пример: `example-data/hmbee/all_json.curl.txt`), ответ — объект, значения которого суть записи (`Object.values`). Файл большой (~10 МБ за всю историю). Записи различаются по `type` (`unplanned` | `planned`), `subtype` (`e`/`i`/`t`), `real_amount`, `plan_amount`, `category`, `account_id`, `date`. В Хани Мани `type=planned` НЕ меняется при подтверждении — подтверждённость определяется наличием `real_amount`.

Счета Точки в Хани Мани: `2053036`, `5737785`, `5737786`, `8846259`.

Этот change — первый шаг к матчингу плановых транзакций; полноценный планнинг-матчер (подтверждение планов с допусками и окном месяца) делается отдельно.

## Goals / Non-Goals

**Goals:**
- `sync --update-hmbee-cache` выгружает транзакции Хани Мани и кладёт обрезанный по дате кеш в `sync/hmbee/all_json_cache.json`.
- `apply` использует кеш, чтобы помечать уже внесённые транзакции как `identified=true, save=false, reason="Внесена вручную"` и не писать их.
- Поведение видно в `--preview`; покрыто unit-тестами.

**Non-Goals:**
- Подтверждение плановых транзакций (default/extended алгоритмы, tolerance, окно месяца, PATCH) — отдельный change.
- Режим `apply --preview-planned`.
- Слияния «1 реальная → N планов» (аренда+ЖКХ, Маша+Школа).
- Авто-инвалидация кеша после записи.

## Decisions

### 1. Кеш управляется командой `sync`, а не `apply`
`--update-hmbee-cache` — флаг к `sync`. Период (`--from`) уже есть у `sync`, и именно он задаёт границу обрезки (`--from − 10 дней`). `apply` остаётся без параметра периода и просто читает готовый кеш.
- *Альтернатива (отклонена):* период и кеш на стороне `apply`. У `apply` сейчас нет дат, а у `sync` есть; дублировать период не нужно.
- *Следствие:* при смене периода кеш переобновляется тем же `sync --update-hmbee-cache`, что снимает проблему «кеш обрезан под другой период».

### 2. Ручное обновление кеша (принятый компромисс)
Кеш обновляется только явным `sync --update-hmbee-cache`. После записи в Хани Мани кеш устаревает; дисциплина — обновлять кеш перед `apply`, если были ручные правки или предыдущий `apply` уже писал.
- *Альтернатива (отложена):* авто-инвалидация/дозапись кеша после `createTransaction`. Полезно, но вне охвата — добавим отдельно.
- *Риск* зафиксирован ниже.

### 3. Индекс «реально внесённых» = записи с `real_amount != null`
Включаем `unplanned` ∪ `planned`-с-`real_amount`; неподтверждённые планы (только `plan_amount`) игнорируем. Это единый признак «деньги реально прошли».

### 4. Ключ сопоставления и направление
Ключ: `account_id + date + round(amount) + direction + category`.
- `direction` ↔ `subtype`: `e`=expense, `i`=income, `t`=transfer.
- Для `subtype=t` категория в Хани Мани `null`, поэтому из ключа исключается (матч по `account_id + date + round(amount) + direction`).
- Суммы сравниваются после `Math.round` (Точка — дроби/копейки, Хани Мани — целые).
- Дата берётся из транзакции источника с фолбэком на `meta_data.time_data.event_date` для карточных записей (у них `data.date` пустой). Это же поле используется при обрезке кеша.
- Валюта входит в ключ (есть планы в usd/eur).

### 5. Жадное сопоставление 1:1
Каждая запись кеша «съедается» максимум один раз. Реализация: индекс — это `Map<key, MutableList>`; при матче запись изымается из списка. Это не даёт нескольким одинаковым суммам за день (частый кейс карт) схлопнуться на одну запись Хани Мани.

### 6. Где живёт skip в пайплайне
Skip — пост-проход в `apply` после нормализации: для каждого `PreviewRecord` с заполненным `hmbee`/`normalized` пытаемся изъять матч из индекса; при успехе ставим `identified=true, save=false, reason="Внесена вручную"`. Существующая запись через `save=false` уже исключается из write-path, поэтому `source-apply` менять не нужно. Skip-записи показываются в `--preview` (и проходят `--only-errors`, т.к. `save=false`).

### 7. Новый метод клиента `getAllTransactions`
GET `all_json.json` с теми же auth-заголовками, что у `createTransaction` (`user-email`, `user-token`, `hm-source`, cookie из env). Ответ парсится Zod-схемой и нормализуется через `Object.values`. Ошибки — без раскрытия секретов.

## Risks / Trade-offs

- **Устаревший кеш → дубли или пропущенный skip.** Кеш не видит свежих ручных правок и собственных записей предыдущего `apply`. → Дисциплина ручного обновления; `apply` в verbose-режиме печатает дату/возраст кеша, чтобы оператор замечал устаревание. Авто-инвалидация — отдельный change.
- **Категория источника ≠ категория ручной записи.** Skip по категории сработает только если маппинг даёт ту же категорию, что выбрал оператор. Для произвольных ручных unplanned возможен промах → дубль. Объём низок (бот замещает ручной ввод). Принимаем; для переводов категория и так исключена.
- **Допущение: у confirmed-планов дата скорректирована под реальную банковскую** (даёт точный матч по дате). На данных есть лёгкая неоднозначность. → На этапе тестов прогнать `apply` по реально-веденному месяцу и проверить совпадение дат 1:1; если не сходится — добавить узкое окно ±N только для ветки confirmed-планов (вне текущего охвата, но точка расширения предусмотрена).
- **Размер ответа `all_json` (~10 МБ).** → Обрезка по `--from − 10 дней` уменьшает файл кеша; полный ответ в памяти на время обрезки приемлем.

## Open Questions

- Нужно ли печатать в `apply` сводку «сколько пропущено как ручной ввод» и возраст кеша по умолчанию или только в verbose? (Склоняемся к verbose.)
- Поведение `apply`, если кеш `sync/hmbee/all_json_cache.json` отсутствует: жёсткая ошибка с подсказкой запустить `sync --update-hmbee-cache`, либо мягкое предупреждение и продолжение без skip? (Предлагается явная ошибка, чтобы не записать дубли по незнанию.)
