# Design — apply-block-unresolved

## Контекст

Non-preview `apply` в `src/index.ts` строит `previewRecords` (normalize → `applySkipPass` → `applyMatchPass`), затем фильтрует `isReadyForApply` и отправляет их через `dispatchTransaction`. Не-ready записи сейчас просто не попадают в отправку — молча.

## Таксономия пропусков

Разбор реального файла даёт исчерпывающий набор reason'ов:

| identified | save | reason | природа | блокирует? |
|---|---|---|---|---|
| false | false | error-строка (парс, unsupported type_code, missing field) | ошибка | 🔴 да |
| true | false | `Category is missing for income or expense transaction` | ошибка маппинга | 🔴 да |
| true | false | `excluded` | штатный дизайн (вторая нога перевода и т.п.) | 🟢 нет |
| true | false | `Внесена вручную` | штатный дедуп | 🟢 нет |
| true | true | `null` | отправляется | — |

**Определение проблемной записи:** `!identified || (!save && reason ∉ EXPECTED_SKIP_REASONS)`, где `EXPECTED_SKIP_REASONS = { "excluded", "Внесена вручную" }`.

Выбран allowlist ожидаемых пропусков (а не denylist проблемных): любой новый/незнакомый `reason` при `save = false` по умолчанию трактуется как проблема — безопасная сторона по умолчанию (fail loud).

## Точка внедрения

Проверка ставится в non-preview ветке `apply` **после** построения `previewRecords` и **до** любого `dispatchTransaction`. При наличии проблемных записей — печать списка (id из `normalized.transactionId`, описание, `reason`) в `stderr` и завершение с ненулевым кодом; ни одна запись не отправляется (all-or-nothing).

Preview-ветки (`--preview`, `--preview-planned`) не затрагиваются: они и есть инструмент разбора проблемных записей (вместе с `--only-errors`).

## Взаимодействие с --only-id

Гейтинг оценивает **полный** нормализованный набор, а не только выбранные `--only-id`. Обоснование: цель — не дать применить, пока в наборе есть неразобранные проблемы; `--only-id` не должен служить обходом. Это осознанный выбор (соответствует «без возможности пропустить»); при необходимости может быть пересмотрен отдельным change.

## Engineering Constraints

- **Error handling:** блокировка реализуется как ранний выход с явным сообщением и списком; не глотать и не логировать вполголоса. Exit code ненулевой.
- **Type safety:** переиспользовать существующие поля `PreviewRecord` (`identified`, `save`, `reason`); строковые reason-константы вынести/переиспользовать (`MISSING_CATEGORY_REASON` уже есть; «Внесена вручную» — в `skipIndex.ts`), не хардкодить магические строки в нескольких местах.
- **Module boundary:** логику «является ли запись проблемной» держать чистой функцией (тестируемой) над `PreviewRecord[]`, отдельно от I/O печати.
- **Testing:** юнит-тесты на классификатор проблемных записей (каждая строка таблицы) и на то, что при наличии проблемной записи отправка не вызывается.
- **Style/lint:** `npm run check` — часть DoD.

## Риски

- **Жёсткость:** одна незамапленная категория блокирует весь батч. Это намеренно (выбор оператора); диагностика через `--preview --only-errors` остаётся доступной для разбора.
