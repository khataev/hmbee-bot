## Context

`scripts/tochka-mapping.js` — интерактивный REPL (plain JS ESM, запуск `node scripts/tochka-mapping.js`), проходящий по записям файла `sync/tochka/*.json`. По каждой записи оператор вводит команду:
- `m, Категория[, Описание]` — mcc-маппинг;
- `t, Категория[, Описание]` — title-маппинг (с проверкой self-match как regex);
- `i`/`im`/`it` — добавить в `ignored`;
- Enter — пропуск, `q` — стоп.

Дедуп: запись авто-пропускается, если её `mcc` уже в `existingMcc`, или `title` матчится одним из `titleRegexes`, или попадает в `ignored`. Пишет только `config/sources.json` (`CONFIG_PATH`), сохраняя форматирование через сырой JSON read/write.

Runtime (родительский change) уже поддерживает `hmbee.categoryMapping.rules` — массив правил `{ when: <JSONLogic>, category, description? }`, вычисляемых `evaluateRule` с кастомным оператором `matches` (regex, case-insensitive). Реальные правила используют идиому `AND(type_code == X, matches(substr, поле))`.

## Goals / Non-Goals

**Goals:**
- Команда `r, <field>, <Категория>[, <Описание>]` создаёт правило и дописывает в `rules[]`.
- Правило собирается по идиоме `AND(type_code guard, matches(полное поле, поле))`.
- Валидация наличия `record.data.<field>` перед созданием.
- Вывод `type_code` и `event_date` в инфо-строке записи.
- Скрипт остаётся plain JS, не тянет `json-logic-js`, не вычисляет правила.

**Non-Goals:**
- Вычисление правил / участие `rules[]` в авто-пропуске (дедуп остаётся title/mcc).
- Вариант правила без guard.
- Сужение подстроки в `matches` и экранирование regex — ручная правка оператором.
- Запись в `config/sources.example.json` (скрипт и сейчас пишет только `sources.json`).
- Редактирование/удаление существующих правил через скрипт.

## Decisions

### Решение 1: Скрипт только создаёт правила, не вычисляет их
Создание правила — это построение JS-объекта и запись в конфиг, никакой логики JSON Logic не требуется. Поэтому скрипт не импортирует `json-logic-js` и не регистрирует `matches`.

_Почему это важно:_ если бы скрипт вычислял правила (например для авто-пропуска), ему понадобилась бы своя копия оператора `matches`. Две независимые реализации одной семантики (`new RegExp(pattern, 'i').test(String(value))`) со временем разошлись бы («дрифт»): изменили бы runtime-версию, а копию в скрипте забыли — и скрипт считал бы совпадения иначе, чем движок при apply. Отказ от вычисления в скрипте устраняет этот риск по построению.

_Следствие:_ запись, покрытая только правилом `rules[]`, не будет авто-пропущена (дедуп смотрит лишь title/mcc) и может быть переспрошена. Принято как приемлемое ограничение.

### Решение 2: Guard по type_code всегда
Правило собирается как `{ and: [ { "==": [ {var: type_code}, <тип записи> ] }, { matches: [<поле>, {var: record.data.<field>}] } ] }`. Guard привязывает правило к типу записи, из которой оно создано, и не даёт `matches` по общему полю (например `purpose`) случайно зацепить другое семейство записей. Вариант без guard не поддерживается — упрощает грамматику команды и совпадает с уже написанными вручную правилами.

_Альтернатива:_ опциональный guard (`r!`). Отклонено пользователем — на практике правила всегда привязаны к типу.

### Решение 3: В matches идёт полное содержимое поля
Скрипт подставляет `record.data.<field>` целиком как паттерн `matches`. Сужение до нужной подстроки и экранирование regex-метасимволов оператор делает вручную позже. Это согласуется с поведением title-паттернов, где корректность паттерна — ответственность оператора.

### Решение 4: Валидация наличия поля
Перед сборкой правила проверяется `record.data.<field>`: если `undefined`/пусто — правило не создаётся, печатается предупреждение, управление возвращается к промпту той же записи. Защищает от опечатки в имени поля и от поля, отсутствующего у данного типа записи (`phoneNumber` у `CardTransactionInfo`).

### Решение 5: Append в конец rules[]
Новое правило дописывается в конец массива. Правила узкие и guard-нутые, first-match-wins в runtime → затенение маловероятно. Позицию при необходимости оператор меняет вручную.

### Решение 6: Грамматика команды в существующем стиле
`r, <field>, <Категория>[, <Описание>]` парсится по тем же правилам, что `m`/`t` (разбор по запятым, опциональное описание, нормализация кавычек категории через существующий `normalizeCategory`). Первое поле после `r` — имя поля в `record.data`.

## Risks / Trade-offs

- **Правило создано по полю с пустым/отсутствующим значением** → Митигация: валидация (Решение 4) отменяет создание.
- **Полное содержимое поля как regex ловит слишком много/мало** → Ожидаемо; оператор сужает вручную. Документируется в выводе/подсказке.
- **Правило не участвует в авто-пропуске** → Осознанное ограничение (Решение 1); в худшем случае запись переспрашивается, дублирующее правило оператор не создаёт визуально видя `type_code`.
- **Некорректный regex в полном значении поля** (спецсимволы) → это конфигурационная проблема, ловится на стороне runtime (`evaluateRule` оборачивает в try/catch → правило не матчится); скрипт паттерн не проверяет, как и для title.

## Migration Plan

- Аддитивное изменение скрипта: команды `m`/`t`/`i` не меняются, добавляется `r` и два поля в выводе.
- Конфиги без `rules` продолжают работать; ключ `rules` создаётся лениво при первом `r` (по образцу `getCategoryMapping`, гарантирующего наличие под-структур).
- Rollback — обратимо: правила можно удалить из конфига вручную; откат кода скрипта не влияет на уже записанные правила.
