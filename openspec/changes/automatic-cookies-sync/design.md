## Context

Точка использует session-cookie для авторизации к внутреннему web-API `https://i.tochka.com/api/v1/timeline`. Оператор вручную копирует cookie из DevTools в `TOCHKA_COOKIE` (`.env`). Официального OAuth-API для этого потока мы не используем, backend не контролируем — значит стандартные схемы (OAuth PKCE / device grant) неприменимы: они требуют, чтобы провайдер зарегистрировал наше приложение.

Эмпирические факты, установленные при исследовании (Firefox, профиль `*.default-release`):

- Нужные Точке токены — **session-cookie** (`Expires = Session`): `X-CSRF-TOKEN`, `RsRememberMeToken` (на `.tochka.com`), `JSESSIONID` (на `i.tochka.com`). Поэтому в `cookies.sqlite` их **нет** (туда попадают только persistent-cookie).
- Эти же токены **присутствуют** в Firefox sessionstore `sessionstore-backups/recovery.jsonlz4` — Firefox держит там session-cookie для восстановления сессии/после падения, независимо от настройки «восстанавливать предыдущую сессию». Проверено декодированием файла: `RsRememberMeToken`, `X-CSRF-TOKEN`, `JSESSIONID` и остальные ключи на месте.
- HM (`app1.hmbee.ru`) авторизуется заголовком `user-token`, а не cookie: заполнение `HM_COOKIE` случайными данными не ломает синк. Значит для HM cookie-источник не нужен вовсе.

Формат `*.jsonlz4` — это **mozLz4**: 8-байтная сигнатура `mozLz40\0`, затем `uint32 LE` (размер распакованных данных), затем raw LZ4-блок (не LZ4 frame — стандартный `lz4` CLI его не читает).

Ограничения проекта: TypeScript strict, Biome, Definition of Done = `npm run check`. Новых runtime-зависимостей избегаем.

## Goals / Non-Goals

**Goals:**
- Убрать ручной перенос cookie для Точки: инструмент сам читает свежую cookie из браузера.
- Ввести шов `CredentialProvider` (`getSession(system)`), за которым скрыт источник cookie, чтобы будущие банки/источники подключались без изменения адаптеров.
- Сохранить ручной `TOCHKA_COOKIE` из `.env` как fallback.
- Не менять контракт `src/adapters/tochka.ts` (он уже принимает cookie-строку).
- Убрать неавторизующий `HM_COOKIE` из HM-запросов и из обязательных секретов.

**Non-Goals:**
- Автоматический headless-логин/релогин (Playwright) и браузерное расширение — вне scope; ручной вход в браузер остаётся за оператором.
- Поддержка Chrome/Chromium как источника (шифрование значений через Keychain) — не в этом change.
- Поддержка token-based банков через этот бэкенд — это отдельный бэкенд за тем же швом в будущем.
- Автообновление/продление самой сессии Точки — не решаем; при протухании оператор логинится в браузере заново.

## Decisions

### D1. Источник cookie — Firefox sessionstore (`recovery.jsonlz4`), а не `cookies.sqlite`
Нужные токены session-scoped и в `cookies.sqlite` физически отсутствуют. Sessionstore — единственный файловый источник, где они есть.
- **Альтернативы:** `cookies.sqlite` (yt-dlp-стиль) — не содержит session-cookie, отпадает. Live-reader через расширение/Playwright — читает session-cookie штатно, но тяжелее (бинарь/второй артефакт) и вне выбранного file-based подхода.
- **Рабочий сценарий — Firefox открыт.** Оператор логинится в Точку и оставляет вкладку открытой; синк запускается при работающем Firefox. Тогда достаточно `recovery.jsonlz4` (пишется на ходу). Случай закрытого Firefox (`sessionstore.jsonlz4`) в первой итерации не поддерживается — см. D7.
- **Порядок выбора файла:** `recovery.jsonlz4` → при отсутствии/повреждении → `recovery.baklz4` (резервный снимок того же формата). Оба — снимки при работающем Firefox.

### D2. Шов `CredentialProvider.getSession(system)`
Единая точка получения cookie-строки; бэкенд (Firefox-sessionstore) — сменная реализация за интерфейсом. Адаптеры не знают, откуда пришла cookie.
- **Альтернатива:** дергать чтение sessionstore прямо в `tochka.ts` — связало бы адаптер с источником и мешало бы добавлять банки/бэкенды.

### D3. mozLz4-декодер — zero-dependency
LZ4-block-декомпрессия реализуется вручную (~30 строк): проверка сигнатуры, чтение размера, декод raw-блока. Новых npm-пакетов не добавляем.
- **Альтернатива:** npm-пакет `lz4`/`mozlz4` — лишняя зависимость и нативные бинарники ради тривиального алгоритма.

### D4. Доменная фильтрация по cookie-matching, а не хардкод ключей
Собираем все cookie, которые браузер отправил бы на `i.tochka.com`: хосты `i.tochka.com`, `.tochka.com`, `tochka.com` (суффиксный матчинг domain-атрибута). `id.tochka.com`-scoped cookie (`t_uid`, `TochkaID`, `ID-CSRF-TOKEN`) **исключаем** — они на таймлайн не уходят. Хардкод «важных» ключей запрещён: набор ключей может меняться.
- **Дедупликация:** в sessionstore встречаются дубли (несколько окон) — схлопываем по `(host, name)`.

### D5. Fallback на `.env`
Если браузерный бэкенд не нашёл cookie (Firefox не установлен, профиль пуст, файл отсутствует/устал), `CredentialProvider` использует `TOCHKA_COOKIE` из env. `TOCHKA_COOKIE` становится опциональным.

### D6. HM — удаление cookie как последний шаг
Заголовок `cookie` убирается из `createTransaction`, `confirmPlannedTransaction` и чтения `all_json`; `HM_COOKIE` уходит из обязательной env-схемы. Делается последней задачей, чтобы не смешивать с основным механизмом.

### D7. Один профиль и только работающий Firefox (scope первой итерации)
У оператора всегда ровно один Firefox-профиль (Firefox не основной браузер), поэтому берём единственный профиль из `profiles.ini` без конфигурации выбора. Синк рассчитан на **работающий** Firefox с открытой залогиненной Точкой → читаем только `recovery.jsonlz4` (+ `recovery.baklz4` как резерв). Случай закрытого Firefox (`sessionstore.jsonlz4`, зависит от настройки восстановления сессии) в первую итерацию не входит.
- **Альтернатива:** поддержать закрытый Firefox сразу — усложняет (нужна включённая «restore session», иначе session-куки теряются) без явной необходимости; добавим позже, если понадобится.

## Risks / Trade-offs

- **Формат sessionstore недокументирован и может меняться между версиями Firefox** → изолируем парсинг в одном модуле; рекурсивный поиск cookie-объектов (по наличию полей `host`/`name`/`value`) устойчив к перестановкам структуры; при сбое — понятная ошибка и fallback на `.env`.
- **`recovery.jsonlz4` отстаёт от live-состояния на ~15с** (Firefox пишет его периодически) → приемлемо для сессии, живущей дольше; при протухании оператор всё равно релогинится.
- **`browser.sessionstore.privacy_level` = 1/2 вырезает cookie из sessionstore** → дефолт `0` (всё сохраняется) работает; поведение и требование к настройке документируем, при отсутствии cookie срабатывает fallback.
- **Залоченный/пишущийся файл при работающем Firefox** → читаем копию файла, а не оригинал.
- **Утечка значений cookie в логи** → значения не логируем; диагностика оперирует только именами cookie.
- **Firefox-специфичность** → осознанное ограничение; другие браузеры/источники — отдельные бэкенды за тем же швом.

## Migration Plan

1. Добавить `CredentialProvider` + Firefox-sessionstore-бэкенд + mozLz4-декодер (за швом, ещё не подключая к адаптеру).
2. Переключить получение cookie в `tochka.ts` на `CredentialProvider` с fallback на `TOCHKA_COOKIE`.
3. Сделать `TOCHKA_COOKIE` опциональным в `env.ts`; обновить `.env.example` / `README.md`.
4. (Последним) убрать `cookie` из HM-запросов и `HM_COOKIE` из обязательной схемы.
- **Rollback:** оставить `TOCHKA_COOKIE` в `.env` — при откате механизма адаптер продолжает работать от env-значения.
