## Context

В `src/apply/preview/tochka.ts` категория для hmbee-транзакции разрешается через захардкоженные:
- `MCC_MAP: Record<string, string>` — MCC-код → категория
- `TITLE_MAP: [string, string][]` — массив пар [подстрока, категория], линейный scan с `includes()`
- `TITLE_REGEX_MAP: [RegExp, string][]` — regex-паттерны, отдельный проход

Маппинг нельзя менять без правки кода. Файл `data/tochka_mapping.txt` пишется скриптом, но нигде не читается. Поле `description` hmbee-транзакции содержит только строку суммы.

## Goals / Non-Goals

**Goals:**
- Маппинг MCC/title хранится в `config/sources.json` под ключом `hmbee.categoryMapping`, загружается через `loadConfig()`.
- Захардкоженные `MCC_MAP` и `TITLE_MAP` полностью удаляются из кода; их содержимое переносится в конфиг.
- `description` транзакции формируется по шаблону `"${amount} ${entry.description}"` если маппинг содержит description.
- Скрипт `tochka-mapping.js` записывает маппинги в `config/sources.json` и `config/sources.example.json`.
- `TITLE_MAP` и `TITLE_REGEX_MAP` объединяются в один тип `[RegExp, MappingEntry][]`; в конфиге паттерны хранятся как строки, при загрузке конвертируются в `RegExp`.
- Скрипт при вводе title-маппинга проверяет, матчится ли сам title с паттерном как regex; при несовпадении — предупреждение и предложение ввести паттерн вручную.

**Non-Goals:**
- Transfer-транзакции — description не трогаем.
- Плановые транзакции (real_amount=undefined) — отдельная задача.
- `TITLE_REGEX_MAP` — в этой итерации не трогаем.

## Decisions

### 1. Хранилище маппинга: `hmbee.categoryMapping` в sources.json

**Структура в конфиге:**
```json
{
  "hmbee": {
    "currenciesMapping": { "810": "rub" },
    "categoryMapping": {
      "mcc": {
        "5411": { "category": "Покупки / Продукты" },
        "5912": { "category": "Покупки / Аптека и БАДы", "description": "аптека" }
      },
      "title": {
        "TIMEWEB.CLOUD": { "category": "Услуги / Хостинги и облака", "description": "TimeWeb" },
        "PDLDK_AI_CLUB": { "category": "Подписки и донаты" }
      }
    }
  }
}
```

**Rationale:** Маппинг — конфигурация приложения, а не runtime-данные. Размещение в `sources.json` даёт: единое место для всех настроек, валидацию через Zod при старте, типизацию через `AppConfig`. Альтернатива — отдельный файл (`data/tochka_mapping.txt`) — уже используется, но не читается кодом и не типизирована.

### 2. Полное удаление захардкоженных MCC_MAP / TITLE_MAP

**Решение:** Удалить константы из `tochka.ts`. Значения перенести в `config/sources.json` и `config/sources.example.json` при реализации.

**Rationale:** Поддержка двух источников (код + конфиг) создаёт неоднозначность приоритетов и дублирование. Одиночный источник истины — конфиг.

### 3. TITLE_MAP + TITLE_REGEX_MAP → единый `[RegExp, MappingEntry][]`

**Решение:** Оба массива объединяются в одну структуру `titleRules: [RegExp, MappingEntry][]`. Substring-matching (`includes`) — частный случай regex без якорей, отдельный тип не нужен. В конфиге паттерны хранятся как строки (`Record<string, MappingEntry>`), при загрузке конвертируются: `Object.entries(config.title).map(([pat, entry]) => [new RegExp(pat, 'i'), entry])`.

**Rationale:** Единый тип — меньше концептуальных слоёв. Паттерны в Record дают дедупликацию по ключу и понятную структуру для ручного редактирования конфига. Поиск в рантайме — всегда O(n) по числу паттернов; структура хранения не влияет на скорость matching.

### 4. Передача маппинга в tochka.ts: через параметр функции

**Решение:** `mapTochkaCategory(description, mcc, categoryMapping)` получает маппинг явным параметром. `previewTochkaRecord(...)` также получает `categoryMapping` из `AppConfig` и пробрасывает вниз.

**Rationale:** Явная передача зависимости позволяет тестировать без моков файловой системы — достаточно передать тестовый объект маппинга. Альтернатива (модульный singleton) затрудняет изоляцию тестов.

### 5. Скрипт tochka-mapping.js: JSON-обновление вместо append

**Решение:** Скрипт читает `config/sources.json`, добавляет/обновляет запись в `hmbee.categoryMapping.mcc` или `hmbee.categoryMapping.title`, записывает файл обратно. То же делает с `config/sources.example.json`.

**Rationale:** Конфиг — структурированный JSON, append-формат JSONL из txt-файла не подходит. Дедупликация обеспечивается природой объекта (ключ перезаписывается).

### 6. Формат ввода скрипта: третье поле + валидация regex для title

Формат ввода:
```
m, Покупки / Продукты
m, Покупки / Продукты, сыродавленное масло
t, Категория[, Описание]
```

Для `t`-маппинга скрипт автоматически проверяет: `new RegExp(titleValue, 'i').test(titleValue)`. Если проверка выбрасывает исключение или возвращает `false` — выводится предупреждение:

```
⚠ Паттерн «YANDEX*5815*PLUS» не матчится с title как regex.
  Введите паттерн вручную (или Enter чтобы сохранить строку as-is):
  > YANDEX.+PLUS
```

Если пользователь вводит паттерн — он сохраняется вместо исходного title. Если нажимает Enter — сохраняется исходный title. Ответственность за корректность паттерна — на пользователе; скрипт не экранирует автоматически.

## Risks / Trade-offs

**[Risk] sources.json разрастается** → Mitigation: маппинг компактен (плоский Record), десятки записей не критичны для JSON-файла.

**[Risk] Одновременная запись скрипта и работа приложения** → Mitigation: скрипт — CLI-инструмент, используется вне работы pipeline; конфликтов нет.

**[Risk] sources.example.json содержит реальные маппинги** → Это нормально: категории — не чувствительные данные, пример конфига полезнее с реальными значениями.
